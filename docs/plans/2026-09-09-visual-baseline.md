# Baseline рендера перед визуальным апгрейдом (фаза 0)

Снято 2026-09-09 на MacBook Air (Apple Silicon), окно 2000×1000, ветка `worktree-visual-baseline`.
Это опорные числа для фаз 1–5 плана «стилизованный реализм»: каждая последующая фаза
сравнивается с ними, а не с замерами роадмапа `2026-07-12-pseudo3d-migration-roadmap.md`
(те снимались год-в-год другим способом и воспроизвести их не удалось).

## Главный вывод

**Рендер не является узким местом — им является симуляция.** С замороженной симуляцией кадр
стоит 13–14 мс, с работающей — 53 мс. При этом vsync-потолок в 60 FPS полностью скрывал это:
под ним обе конфигурации показывали одинаковые ~59.5 FPS.

Практическое следствие для плана: у фаз 1–4 есть реальный запас GPU, но он тоньше, чем кажется
(13 мс из 16.7 при 60 FPS уже заняты). А цель «≥60 FPS» из фазы 5 упирается в симуляцию,
и одними рендер-оптимизациями она не берётся.

## Гарнитура замера

```bash
# сборка и запуск (BRP нужен для автоматизации замера)
SIMCITY_PRESENT_MODE=immediate cargo run --release --features dev
```

`SIMCITY_PRESENT_MODE=immediate` добавлен в этой же фазе (`src/main.rs`), потому что под vsync
baseline бесполезен: он обрезает кадр на 16.7 мс и регрессия рендера становится видна только
после того, как она уже стоила игроку кадров. Без переменной поведение прежнее — `AutoVsync`.

Числа снимаются по BRP из `DebugWorldSnapshot` (FPS/кадр) и `DebugRenderSnapshot` (состав кадра,
добавлен здесь же), 4 отсчёта в секунду, окно 40–60 с, агрегируется медиана.
Медиана, а не среднее: распределение кадров тяжёлохвостое, среднее завышает вдвое.

| Симуляция работает, зум 1.0 | 18.7 | 13.9 | 118.3 | 53.4 | 214 |
| Под vsync, пауза, зум 1.0 | 59.2 | 53.5 | 63.3 | 16.9 | 151 |

Разница «пауза против работы» — около 40 мс на кадр. Это симуляция вместе с dev-сканами мира
(под `dev` каждый кадр крутится ~17 систем полного скана для BRP-зеркал), разделить их этот
замер не может — см. «Чего замер не даёт».

**Батчинг здоров:** ~22 тысячи видимых мешей схлопываются в ~80 групп. Это тот запас, который
фаза 3 обязана не разрушить — рост `distinct_materials` и есть признак «материала на цвет».

**Теневых кастеров почти 5 тысяч.** В фазе 7 роадмапа 800 кастеров роняли кадр 72→22 FPS, так что
это кандидат №1 на профилирование в фазе 5 — и повод не добавлять кастеры в фазе 4.

## Чего замер не даёт

- **День против ночи не разделён.** Пауза — это отдельный `AppState`, и переход в неё дёргает
  путь завершения игры («Game ended»), сбрасывая `City.day/hour` в 1/00:00. То есть все замеры
  «на паузе» сняты при ночном освещении независимо от того, какой час показывал снапшот перед
  паузой. Разделять свет день/ночь придётся другим способом.
- **Вклад dev-сканов не отделён от симуляции.** Оба живут в тех же 40 мс.
- **`visible_mesh_entities` считает видимость в ЛЮБОМ view**, включая каскады теней, а не только
  на экране. Поэтому число прыгает с 11.5к до 19к при неизменной камере.
- **Tracy-прогон не сделан:** установленный Tracy 0.13.1 против `tracy-client-sys` 0.28 в дереве
  зависимостей — версии протокола расходятся. Нужен либо Tracy 0.12.x, либо бамп `tracy-client`.

## Побочные находки

- Лог забит предупреждениями `B0004` (`InheritedVisibility` у ребёнка при родителе без неё) —
  сотни строк за секунды. Не влияет на кадр, но прячет полезный вывод.
- Прямой запуск `target/release/simcity` не работает при фиче `dev`: она тянет
  `bevy/dynamic_linking`, и бинарю не хватает rpath до `libstd`. Запускать через `cargo run`.

## Протокол для следующих фаз

1. Собрать и запустить с `SIMCITY_PRESENT_MODE=immediate cargo run --release --features dev`.
2. Дать прогреться (первые ~30 с — прогрев пайплайнов Metal, кадр нерепрезентативен).
3. Снять два ряда по 40–60 с: на паузе (цена рендера) и в работе (цена игры), зум 1.0.
4. Сравнивать медианы с таблицей выше; `batch_estimate` и `visible_shadow_casters` —
   с таблицей состава.
