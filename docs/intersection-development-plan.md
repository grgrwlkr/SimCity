# План разработки перекрёстков (Две двухполосные дороги)

Этот документ задаёт, как должны работать перекрёстки в нашей игре и как мы это реализуем в коде.
Документ намеренно строгий: без двусмысленной логики движения и без эвристических «угадываний» коннекторов.

## 1) Что покрывает план

Проектируем один канонический тип перекрёстка:
- одна горизонтальная двухполосная дорога (ось запад-восток);
- одна вертикальная двухполосная дорога (ось север-юг);
- правостороннее движение.

Для этого типа фиксируем:
- секции перекрёстка (пронумерованные ячейки);
- все допустимые траектории проезда по секциям;
- правила допуска/конфликтов;
- шаги реализации в системах Bevy.

## 2) Модель движения (как я это понимаю)

Для двусторонних двухполосных дорог с правосторонним движением:
- в этом шаблоне на каждое направление приходится ровно одна полоса;
- до въезда на перекрёсток машина обязана оставаться в своей полосе;
- внутри перекрёстка машина едет по одному детерминированному connector-пути:
  - `Straight`
  - `RightTurn`
  - `LeftTurn`
  - `U-Turn`
- выезд должен происходить в корректную исходящую полосу для этого направления;
- запрещено использовать встречную полосу как «шорткат».

Следствие: поведение на перекрёстке строится не «случайным» tile-A*, а графом манёвров.

## 3) Канонические пронумерованные секции перекрёстка

Легенда:
- `.` = дорожные тайлы вне зоны перекрёстка (подъезд/выезд);
- `01..16` = секции перекрёстка (авторитетное пространство конфликтов);
- стрелки у границ показывают разрешённое направление движения на подъездах.

```text
                       Полоса С -> Ю
                            |
             .    .         v ^    .    .
             .    .       [01][02] .    .
Полоса В -> З < < <   [03][04][05][06]  < < < 
Полоса З -> В > > >   [07][08][09][10]  > > >
             .    .       [11][12] .    .
             .    .         v ^    .    .
                              |
                        Полоса Ю -> С
```

## 4) Входные/выходные полосы для шаблона

Четыре входящие полосы:
- `IN_N` (с севера, движение на юг);
- `IN_S` (с юга, движение на север);
- `IN_W` (с запада, движение на восток);
- `IN_E` (с востока, движение на запад).

И четыре выходящие полосы:
- `OUT_N` (на север, движение на север);
- `OUT_S` (на юг, движение на юг);
- `OUT_W` (на запад, движение на запад);
- `OUT_E` (на восток, движение на восток).

## 5) Все возможные траектории автомобилей

Всего 16 легальных манёвров (4 на каждый вход: направо, прямо, налево, разворот).
Для каждого манёвра задаётся одна каноническая последовательность секций.

### 5.1 Въезд с севера (`IN_N`)

1. Поворот направо (`IN_N -> OUT_W`):
   - Секции: `01 -> 04 -> 03`
2. Прямо (`IN_N -> OUT_S`):
   - Секции: `01 -> 04 -> 08 -> 11`
3. Поворот налево (`IN_N -> OUT_E`):
   - Секции: `01 -> 04 -> 08 -> 09 -> 10`
4. Разворот (`IN_N -> OUT_N`):
   - Секции: `01 -> 04 -> 08 -> 09 -> 05 -> 02`

### 5.2 Въезд с юга (`IN_S`)

5. Поворот направо (`IN_S -> OUT_E`):
   - Секции: `12 -> 09 -> 10`
6. Прямо (`IN_S -> OUT_N`):
   - Секции: `12 -> 09 -> 05 -> 02`
7. Поворот налево (`IN_S -> OUT_W`):
   - Секции: `12 -> 09 -> 05 -> 04 -> 03`
8. Разворот (`IN_S -> OUT_S`):
   - Секции: `12 -> 09 -> 05 -> 04 -> 08 -> 11`

### 5.3 Въезд с запада (`IN_W`)

9. Поворот направо (`IN_W -> OUT_S`):
   - Секции: `07 -> 08 -> 11`
10. Прямо (`IN_W -> OUT_E`):
   - Секции: `07 -> 08 -> 09 -> 10`
11. Поворот налево (`IN_W -> OUT_N`):
   - Секции: `07 -> 08 -> 09 -> 05 -> 02`
12. Разворот (`IN_W -> OUT_W`):
   - Секции: `07 -> 08 -> 09 -> 05 -> 04 -> 03`

### 5.4 Въезд с востока (`IN_E`)

13. Поворот направо (`IN_E -> OUT_N`):
    - Секции: `06 -> 05 -> 02`
14. Прямо (`IN_E -> OUT_W`):
    - Секции: `06 -> 05 -> 04 -> 03`
15. Поворот налево (`IN_E -> OUT_S`):
    - Секции: `06 -> 05 -> 04 -> 08 -> 11`
16. Разворот (`IN_E -> OUT_E`):
   - Секции: `06 -> 05 -> 04 -> 08 -> 09 -> 10`

## 6) Правила конфликтов (граф манёвров)

Каждый манёвр имеет фиксированный `MovementId` и набор занятых секций.
Два манёвра совместимы тогда и только тогда, когда их наборы секций не пересекаются,
либо политика явно разрешает совместное пакетное прохождение одного потока.

Базовая политика:
- «прямо vs прямо во встречном направлении»: допустимо (если нет пересечения секций);
- «направо vs прямо в том же направлении»: допустимо только при пустом пересечении;
- левый поворот — максимально конфликтный, уступает, пока не получит явный grant.

Пешеходные переходы моделируются как дополнительные конфликтные маски, привязанные к секциям.

### 6.1 Специальные правила для `U-Turn`

- `U-Turn` считается отдельным классом манёвра (`MovementClass::UTurn`), а не частным случаем `LeftTurn`.
- Для `U-Turn` используется собственный `section_mask`; совместимость определяется тем же правилом пересечения масок.
- При равенстве условий допуска (оба кандидата без конфликтов) приоритет у не-`U-Turn` манёвров, `U-Turn` обслуживается после них.
- `U-Turn` разрешается только при активной фазе светофора для этого `MovementId` (или отдельной `U-Turn` подфазе, если она задана планом сигналов).
- Если локальная политика перекрёстка запрещает разворот, манёвр должен получать явный отказ и не попадать в fallback-pathing.

## 7) Светофоры и допуск (admission)

Порядок проверки кандидата на въезд:
1. сигнал светофора (фаза разрешает манёвр?);
2. проверка конфликтов секций (`movement bitset`);
3. проверка пропускной способности downstream (в выходной полосе есть место);
4. проверка конфликта с пешеходами;
5. anti-blocking правило.

Если все проверки пройдены, выдаётся токен:
- `AuthorityToken { movement_id, vehicle, issued_tick, ttl_ticks, exit_lane_id }`

Если отказано, обязательно пишется явная причина:
- `SignalClosed`
- `ConflictOccupied`
- `DownstreamFull`
- `PedConflict`
- `AntiBlock`
- `UTurnPolicyBlocked`

## 8) План реализации в Bevy

### 8.1 Контракты данных

Создать/подтвердить:
- `IntersectionSectionId` (логическая секция в шаблоне или её эквивалент на сгенерированной карте);
- `MovementId` со следующими полями:
  - `entry_lane`,
  - `exit_lane`,
  - `section_mask`,
  - `signal_group_id`.

### 8.2 Системы (маленькие и узкие)

1. `build_intersection_sections`
   - отображает тайлы кластера в канонические логические секции;
2. `build_intersection_movements`
   - генерирует 16 контрактов манёвров для этого шаблона;
3. `cache_signal_phase_by_movement`
   - кэширует открытость сигнала на уровне манёвров;
4. `collect_admission_candidates`
   - собирает кандидатов (по одному для head-vehicle на каждом подъезде);
5. `apply_admission`
   - детерминированно выдаёт grant с фиксированным порядком и причинами отказа;
6. `consume_authority_tokens`
   - обновляет состояние токена при пересечении/выезде/таймауте;
7. `debug_intersection_snapshot`
   - публикует grants/denials/active movements.

### 8.3 Переписывание маршрута внутри перекрёстка

Переписывание connector-сегмента никогда не должно «угадывать» Manhattan-эвристикой.
Система обязана выбирать ровно один манёвр из графа:
- `(entry_lane, intended_exit_lane) -> movement_id -> section sequence`.

Если манёвр не найден:
- маршрут помечается невалидным и запрашивается детерминированный reroute;
- ad-hoc connector не строится.

## 9) Чеклист валидации

Для этого шаблона обязательно:
- ни один маршрут не заходит на встречную полосу;
- каждая пара `entry -> exit` маппится в один из 16 легальных манёвров;
- каждый легальный манёвр следует канонической последовательности секций;
- для каждого входа существует ровно один валидный `U-Turn` манёвр в свою обратную полосу;
- `U-Turn` не получает grant при закрытой фазе/локальном запрете;
- grant не выдаётся при конфликте секций;
- grant не выдаётся, если выходная полоса заполнена;
- debug snapshot показывает счётчики причин отказа и активные `MovementId`.

## 10) Ближайшие шаги

1. Реализовать маппинг секций (`IntersectionSectionId`) и хранить его в intersection cache.
2. Заменить fallback pathing для connector на lookup по графу манёвров.
3. Добавить тестовый fixture для этого exact 2x2 two-lane перекрёстка.
4. Добавить 16 golden-тестов: каждый вход x каждый манёвр.
5. Добавить regression-тест: «для валидной пары entry/exit не бывает `exit_dir=None`».

## 11) Перекрёсток дорог по 4 полосы (2+2)

Ниже фиксируется второй канонический шаблон: пересечение дорог, где на каждой дороге 4 полосы
(по 2 полосы в каждом направлении).

### 11.1 Схема, нумерация секций и полос

Легенда:
- `*_IN_R` — входящая правая полоса (ближе к правому краю проезжей части);
- `*_IN_L` — входящая левая полоса (ближе к осевой/разделителю);
- `*_OUT_R`, `*_OUT_L` — соответствующие исходящие полосы;
- `01..32` — логические секции конфликтного пространства перекрёстка.

```text
                               СЕВЕР
                           N_IN_L  N_OUT_L                    
                  N_IN_R(v) (v) (^) (^)N_OUT_R
                        [01][02][03][04]
        W_OUT_R (<) [05][06][07][08][09][10] (<) E_IN_R
ЗАПАД   W_OUT_L (<) [11][12][13][14][15][16] (<) E_IN_L   ВОСТОК
        W_IN_L  (>) [17][18][19][20][21][22] (>) E_OUT_L
        W_IN_R  (>) [23][24][25][26][27][28] (>) E_OUT_R
                        [29][30][31][32]
                 S_OUT_R(v) (v)(^) (^)S_IN_R
                        S_OUT_L  S_IN_L                       
                               ЮГ
```

Привязка граничных секций к полосам:
- Север: `N_IN_R=01`, `N_IN_L=02`, `N_OUT_L=03`, `N_OUT_R=04`.
- Юг: `S_OUT_R=29`, `S_OUT_L=30`, `S_IN_L=31`, `S_IN_R=32`.
- Запад: `W_OUT_R=05`, `W_OUT_L=11`, `W_IN_L=17`, `W_IN_R=23`.
- Восток: `E_IN_R=10`, `E_IN_L=16`, `E_OUT_L=22`, `E_OUT_R=28`.

### 11.2 Жёсткие lane-level правила

- Перестроения внутри секций `01..32` запрещены; смена полосы только до стоп-линии или после выхода.
- Правая входящая полоса (`*_IN_R`) допускает только `RightTurn` и `Straight`.
- Левая входящая полоса (`*_IN_L`) допускает `Straight`, `LeftTurn`, `U-Turn`.
- `RightTurn` всегда завершает манёвр в `*_OUT_R` целевого направления.
- `Straight` сохраняет индекс полосы: `IN_R -> OUT_R`, `IN_L -> OUT_L`.
- `LeftTurn` завершает манёвр в `*_OUT_L` целевого направления.
- `U-Turn` выполняется только из `*_IN_L` и завершает манёвр в `*_OUT_L` обратного направления.
- Любая попытка недопустимого манёвра по полосе должна быть отклонена на этапе планирования, без fallback-эвристик.

### 11.3 Все допустимые пути (lane -> lane)

Всего 20 манёвров (по 5 на каждый подъезд, включая `U-Turn`):

#### С севера
1. `N_IN_R -> OUT_W_R` (`RightTurn`)
2. `N_IN_R -> OUT_S_R` (`Straight`)
3. `N_IN_L -> OUT_S_L` (`Straight`)
4. `N_IN_L -> OUT_E_L` (`LeftTurn`)
5. `N_IN_L -> OUT_N_L` (`U-Turn`)

#### С юга
6. `S_IN_R -> OUT_E_R` (`RightTurn`)
7. `S_IN_R -> OUT_N_R` (`Straight`)
8. `S_IN_L -> OUT_N_L` (`Straight`)
9. `S_IN_L -> OUT_W_L` (`LeftTurn`)
10. `S_IN_L -> OUT_S_L` (`U-Turn`)

#### С запада
11. `W_IN_R -> OUT_S_R` (`RightTurn`)
12. `W_IN_R -> OUT_E_R` (`Straight`)
13. `W_IN_L -> OUT_E_L` (`Straight`)
14. `W_IN_L -> OUT_N_L` (`LeftTurn`)
15. `W_IN_L -> OUT_W_L` (`U-Turn`)

#### С востока
16. `E_IN_R -> OUT_N_R` (`RightTurn`)
17. `E_IN_R -> OUT_W_R` (`Straight`)
18. `E_IN_L -> OUT_W_L` (`Straight`)
19. `E_IN_L -> OUT_S_L` (`LeftTurn`)
20. `E_IN_L -> OUT_E_L` (`U-Turn`)

### 11.3.1 Посекционные маршруты (`01..32`)

Канонические последовательности секций для тех же 20 манёвров:

1. `N_IN_R -> OUT_W_R` (`RightTurn`): `01 -> 06 -> 05`
2. `N_IN_R -> OUT_S_R` (`Straight`): `01 -> 06 -> 12 -> 18 -> 24 -> 29`
3. `N_IN_L -> OUT_S_L` (`Straight`): `02 -> 07 -> 13 -> 19 -> 25 -> 30`
4. `N_IN_L -> OUT_E_L` (`LeftTurn`): `02 -> 07 -> 13 -> 19 -> 20 -> 21 -> 22`
5. `N_IN_L -> OUT_N_L` (`U-Turn`): `02 -> 07 -> 13 -> 19 -> 20 -> 14 -> 08 -> 03`

6. `S_IN_R -> OUT_E_R` (`RightTurn`): `32 -> 27 -> 28`

8. `S_IN_L -> OUT_N_L` (`Straight`): `31 -> 26 -> 20 -> 14 -> 08 -> 03`
9. `S_IN_L -> OUT_W_L` (`LeftTurn`): `31 -> 26 -> 20 -> 14 -> 13 -> 12 -> 11`
10. `S_IN_L -> OUT_S_L` (`U-Turn`): `31 -> 26 -> 20 -> 14 -> 13 -> 19 -> 25 -> 30`

11. `W_IN_R -> OUT_S_R` (`RightTurn`): `23 -> 24 -> 29`
12. `W_IN_R -> OUT_E_R` (`Straight`): `23 -> 24 -> 25 -> 26 -> 27 -> 28`
13. `W_IN_L -> OUT_E_L` (`Straight`): `17 -> 18 -> 19 -> 20 -> 21 -> 22`
14. `W_IN_L -> OUT_N_L` (`LeftTurn`): `17 -> 18 -> 19 -> 20 -> 14 -> 08 -> 03`

### 11.4 Правила конфликтов и допуска для 4-полосного шаблона

- Каждому пункту из списка выше соответствует отдельный `MovementId` и собственный `section_mask`.
- Совместный grant двух манёвров разрешён только при пустом пересечении `section_mask` и отсутствии ped-конфликта.
- `LeftTurn` и `U-Turn` считаются конфликтно-тяжёлыми манёврами: при равенстве условий имеют более низкий приоритет, чем `Straight`/`RightTurn`.
- Для `U-Turn` обязателен отдельный policy-check (`allow_uturn=true`) и открытая фаза сигнала для этого `MovementId`.
- Если целевая полоса (`OUT_*_*`) не имеет downstream capacity, grant запрещён даже при пустом конфликтном наборе.

### 11.5 Светофорные группы (рекомендуемый минимальный контракт)

- `NS_THROUGH_RIGHT`: все `Straight` и `RightTurn` с северного/южного подъезда.
- `NS_LEFT_UTURN`: `LeftTurn` и `U-Turn` с северного/южного подъезда.
- `EW_THROUGH_RIGHT`: все `Straight` и `RightTurn` с восточного/западного подъезда.
- `EW_LEFT_UTURN`: `LeftTurn` и `U-Turn` с восточного/западного подъезда.

### 11.6 Проверки для тестов

- Ровно 20 валидных lane-level манёвров (`MovementId`) присутствуют в графе.
- Недопустимые пары полоса/манёвр (например, `*_IN_R + LeftTurn`) стабильно отклоняются.
- Внутри `01..32` ни один маршрут не содержит lane change.
- Для каждого `U-Turn` проверяется policy-gate и signal-gate.
- При активном downstream block grant не выдаётся даже для бесконфликтного `RightTurn`.
