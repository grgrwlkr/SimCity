# Traffic v2: реалистичные ПДД, микросимуляция транспорта и пешеходов (спецификация)

**Дата:** 2025-12-24  
**Статус:** дизайн-документ (код не пишем)  
**Контекст:** проект SimCity (Bevy/Rust), текущие доки: `docs/traffic-vehicles-architecture.md`, `docs/roads-architecture.md`, `docs/intersections-architecture.md` (не изменяем).

---

## 0) TL;DR — ключевые решения

1. **Не ломаем базовую модель дорог:** текущий подход “каждая полоса = отдельный тайл” (`RoadCell`) остаётся источником правды в `MapGrid`.
2. **Вводим “логический перекрёсток”** как кластер соседних тайлов `RoadDir::None` (flood fill).  
   **Один светофор = один логический перекрёсток** (не на тайл, а на кластер).
3. **Переписываем симуляцию движения** как микросим:
   - **продольная динамика**: IDM (Intelligent Driver Model) / аналог;
   - **поперечные манёвры**: MOBIL/эвристики для перестроений + правило “держись правее, обгоняй слева”.
4. **Перекрёстки делаем безопасными** через:
   - контроллер приоритета / светофора на логическом перекрёстке;
   - запрет “block the box” (не въезжать без выхода);
   - опционально: **резервации конфликтных зон** внутри перекрёстка (чтобы гарантировать “не нарушает”).
5. **Добавляем пешеходов** через виртуальную инфраструктуру:
   - **тротуары** вдоль внешних границ проезжей части (не расширяем дороги на тайлах);
   - **пешеходные переходы** (зебры) на подходах к перекрёсткам;
   - связка со светофором: пешеходные фазы, “walk / flashing don’t walk”.
6. **Убираем “читерные” анти-джем хаки** (yield как “парковка на обочине”, случайные телепорты) как поведение по умолчанию.  
   Вместо этого: корректные правила проезда + резервации + формализованные развороты (U-turn) + крайний “эвакуатор/деспаун” как аварийная защита стабильности.

## 1) Термины и соглашения

- **Тайл**: клетка `MapGrid` (`TilePos`).
- **Lane tile / тайл полосы**: тайл, где `cell.road.is_some() == true` и `road.dir != None` (обычная полоса).
- **Intersection tile / тайл перекрёстка**: тайл дороги, где `road.dir == RoadDir::None` (сейчас это маркер перекрёстка).
- **Логический перекрёсток (IntersectionCluster)**: множество смежных intersection tiles (4-соседство), образующее единый узел пересечения дорог.
- **Подход (approach)**: набор lane tiles, входящих в IntersectionCluster (по направлению движения).
- **Манёвр на перекрёстке**: `Straight | Left | Right | UTurn` (UTurn — опционально и сильно ограниченно).
- **Опережение**: обгон/объезд в рамках доступных попутных полос (lane-change в “левее” и обратно).
- **Обгон по встречке**: временный выезд на встречную полосу на двухполосной дороге (1+1) для опережения медленного лидера.
- **ПДД v2 (rule-set)**: набор правил движения “как в реальном мире” в рамках упрощений симуляции.

### 1.1 Масштаб и единицы измерения (принято)

В проекте уже есть `MapConfig.tile_size` (world units, используется для рендера/позиционирования). Для реалистичной микрофизики v2 вводим отдельную конвенцию **“тайл → метры”**:

- **Базовая идея**: 1 тайл = \(T\) метров (константа/конфиг, не обязательно равная `tile_size`).
- **Привязка к зданиям**: “обычный 1-этажный дом с участком” = **2×3 тайла** (**2 вдоль улицы**, **3 вглубь квартала**). Это даёт реальный размер участка:
  - ширина участка ≈ \(2T\) м
  - глубина участка ≈ \(3T\) м
  - площадь ≈ \(6T^2\) м²

**Выбранный эталон:** участок **20×30 м**, то есть:
- **\(T = 10\) м на тайл**

**Примечание (принято):** в текущем коде футпринты зданий могут пока оставаться “как сейчас” (якорная клетка 1 тайл).  
Масштаб \(T = 10\) м — это конвенция для физики/пешеходов и будущего расширения строительства, без немедленной переработки размещения зданий.

Скоростные лимиты `RoadKind.speed_limit()` (40/60/80) трактуем как **км/ч** и конвертируем в м/с: \(v_{mps} = v_{kmh}/3.6\).

**Связь “метры ↔ world units”:**
- `tile_size` = world units на тайл (сейчас 16.0 по дефолту).
- тогда \(meters\_per\_world\_unit = T / tile\_size\).

## 2) Текущее состояние (v1) — что уже есть в коде

### 2.1 Дороги и полосы

- `RoadCell` уже хранит: `kind`, `dir`, `lane`, `flow`, `lane_type` (`src/game/roads.rs`).
- Дорога рисуется “по центру”, но физически занимает **N тайлов по ширине**, где N = число полос (2/4/6).  
  `emit_road_commands()` раскладывает lane tiles перпендикулярно “каноническому” направлению (East или North) (`src/game/map/mod.rs`).

### 2.2 Перекрёстки

- Пересечение разных осей при `SetRoad` конвертирует тайл в `dir=None` (intersection tile) (`apply_game_commands_to_grid()`).
- Для многополосных дорог перекрёсток становится прямоугольным кластером `dir=None` (например 4×4).

### 2.3 Маршрутизация

- `RoadGraph` строится как per-tile 4-bit mask связей (`src/game/transport.rs`).
- В графе уже зашиты:
  - запреты движения “против направления” и на встречку;
  - смены полос на соседнюю;
  - вход/выход/движение внутри `dir=None` (сейчас реализовано как “циркуляция по периметру”, чтобы не было нелегальных диагоналей).
- A* учитывает загруженность, штраф за lane-change и поворот, и даёт дополнительный penalty за светофор (через `IntersectionIndex.traffic_light_positions`).

### 2.4 Симуляция транспорта

- `Vehicle` хранит `route: Vec<TilePos>`, `progress` [0..1], `speed`, `max_speed`, `max_accel` (`src/game/traffic.rs`).
- Есть простая “физика” скорости и торможения, очередь перед светофором, “don’t block the box”, а также jam recovery (yield/uturn/деспаун).

### 2.5 Светофоры

- Сейчас светофор привязан к **одному тайлу** (через `TilePos`), и индексируется `traffic_light_positions: HashSet<TilePos>` (`src/game/intersections.rs`).
- Для большого перекрёстка (кластер `dir=None`) это не соответствует требованию: **можно поставить несколько светофоров на разные тайлы одного перекрёстка**.

### 2.6 Пешеходов нет

- Нет модели тротуара, переходов, pedestrian routing и конфликтов с машинами.

## 3) Требования к v2 (что именно хотим получить)

### 3.1 Функциональные требования

1. **Реалистичные правила движения**:
   - соблюдение направления и “проезжих частей” (без езды по встречке/обочине вне разрешённых манёвров);
   - соблюдение скоростных режимов (по `RoadKind`, плюс поведенческие коэффициенты водителя);
   - корректные перестроения и повороты с учётом разрешённых полос (`lane_type`) и физической безопасности.
2. **Реалистичная динамика**:
   - плавный набор скорости / торможение;
   - “следование за лидером” (safe headway), образование волн торможения.
3. **Опережение и обгоны**:
   - опережение в попутных полосах (перестроение для обгона и возврат);
   - обгон по встречке на 1+1 дорогах, но **только при строгих условиях безопасности и запрета нарушений**.
4. **Перекрёстки и светофоры**:
   - логический перекрёсток = кластер `dir=None`;
   - **ровно один светофор/контроллер на один логический перекрёсток**;
   - светофор работает “как в жизни”: зелёный/жёлтый/красный, clearance (all-red), логика “если на жёлтый уже поздно тормозить — проезжай”.
5. **Пешеходы**:
   - тротуары вдоль проезжей части;
   - пешеходные переходы на перекрёстках;
   - взаимодействие со светофорами и приоритетами (пешеходы/повороты).

### 3.2 Нефункциональные требования

- **Производительность**: целевой масштаб v1 (до ~1500 машин) должен оставаться рабочим на FixedUpdate.
- **Детерминизм и предсказуемость**: симуляция должна быть стабильной (без “взрыва” колебаний и бесконечных перестроений).
- **Отладочность**: нужны оверлеи/инструменты для диагностики (в документе описываем, код — позже).

## 4) Архитектура v2: слои и ответственность

### 4.1 Общая схема

```
MapGrid (source of truth: RoadCell per tile)
        │
        ▼ (GraphUpdate, по GraphVersion)
Topology V2 (derived, read-only):
  - LaneTopology (сегменты/смежности)
  - IntersectionTopology (кластеры, подходы, переходы)
  - Sidewalk & Crosswalk Topology (пешеходные ребра)
        │
        ├──────────────┐
        ▼              ▼
Intersection Controllers     Routing (cars + pedestrians)
(lights/priorities)         (high-level, cheap)
        │              │
        └──────┬───────┘
               ▼
Micro-sim tick (FixedUpdate):
  1) perception/sensing
  2) rule evaluation (PДД)
  3) longitudinal (IDM) + lateral (MOBIL)
  4) intersection admission/reservation
  5) integrate movement
  6) metrics/occupancy
```

### 4.2 Что остаётся, а что переписываем

- **Оставляем**: `MapGrid`, `RoadCell`-модель дорог, идею `GraphVersion`, общую механику trips (`TripRequested/TripFinished`).
- **Переписываем**: `traffic.rs` (движение), intersection model (кластеризация), взаимодействие со светофором, перестроения/обгоны, добавляем pedestrians.
- **Модифицируем** (в будущем кодом): `intersections.rs`, `transport.rs`, `map/mod.rs` (только там, где нужно для 1-светофора-на-кластер и для пешеходной инфраструктуры).

## 5) Топология v2: логические перекрёстки, подходы, тротуары, переходы

### 5.1 IntersectionCluster: как выделять “один перекрёсток”

**Источник:** тайлы `cell.road.is_some() && cell.road.dir == RoadDir::None`.

**Алгоритм:** flood fill по 4-соседству:
- найти неразмеченный intersection tile;
- BFS/DFS собрать все смежные `dir=None`;
- это и есть **IntersectionCluster**.

**Результат:**

```text
IntersectionId = последовательный id (u32) в порядке обнаружения

IntersectionCluster:
  - id
  - tiles: Vec<TilePos>
  - aabb: (min_x, min_y, max_x, max_y)
  - centroid_world: Vec2 (для визуала/иконок)
  - boundary: набор “границ” (тайлы, у которых есть сосед не из кластера)
```

**Важно:** IntersectionId должен быть стабилен внутри одной версии графа (`GraphVersion`). Для сохранений можно хранить “ключ” кластера как нормализованный AABB + хэш списка tiles.

### 5.2 Подходы (approaches) и стоп-линии

**Цель:** для каждого кластера определить, откуда машины могут въехать, и где они должны останавливаться.

Подход — это lane tile, который:
- соседствует с любым тайлом кластера;
- имеет `dir != None`;
- и направлен **внутрь** перекрёстка (т.е. `lane_pos + lane_dir.delta() == some intersection tile`).

Для каждого подхода строим:
- `ApproachId` (внутри IntersectionId),
- `entry_lane_tiles: Vec<TilePos>` (полосы, входящие в перекрёсток),
- `stop_line`: геометрия в world coords (обычно у границы кластера, с offset ~0.15 тайла как сейчас),
- `approach_dir`: `RoadDir` (направление движения при въезде).

### 5.3 Манёвры и коннекторы (траектории через перекрёсток)

Текущий `RoadGraph` проводит транспорт внутри кластера как “циркуляцию”, что полезно как защита от нелегальных диагоналей, но **не похоже на реальное движение**.

**v2 подход:** внутри перекрёстка машины едут по **коннекторам** (виртуальные траектории), которые:
- начинаются на стоп-линии подхода,
- заканчиваются на выходной полосе,
- имеют длину, направление, набор конфликтов (см. ниже).

```text
Connector:
  - from_approach (dir, lane index / lane tile set)
  - to_exit (dir, lane tile set)
  - maneuver: Straight | Left | Right | UTurn
  - path: polyline/spline в world coords (приближение достаточно)
  - conflicts: набор ConflictZoneId (пересечения с другими коннекторами/переходами)
```

**Генерация коннекторов (эвристика для grid перекрёстков):**
- прямой: соединяем середину входа с серединой выхода по оси;
- правый поворот: quarter-arc около ближнего угла;
- левый поворот: arc через центр, но с сохранением “правосторонней геометрии”.

Это даст реалистичный визуал и базу для конфликтов/резерваций.

### 5.4 Conflict zones (конфликтные зоны)

Чтобы гарантировать “не нарушает” и не допускает столкновений в пределах перекрёстка, вводим дискретные зоны:

```text
ConflictZone:
  - id
  - shape: AABB/круг/тайловый набор внутри IntersectionCluster
  - used_by: список ConnectorId и CrosswalkId
```

Минимальный вариант — разбить перекрёсток на:
- 1–4 зоны для центра,
- зоны для каждого угла,
- зоны для каждой зебры.

### 5.5 Тротуары: как добавить, не раздувая MapGrid

Так как в текущей модели дорога уже “съедает” N тайлов по ширине, добавлять ещё по тайлу на тротуар ухудшит плотность города.

**Предлагаемая модель:** тротуары — **виртуальные пути в world coords**, построенные вдоль внешней границы проезжей части.

**Идея:**
- для каждого lane-segment (набор lane tiles), определяем “внешнюю границу” слева и справа;
- строим 2 полилинии тротуара (left/right sidewalk);
- на перекрёстках соединяем их угловыми сегментами.

Тротуары не занимают отдельные тайлы, но могут быть отрисованы и использованы пешеходным pathfinding.

**Ограничение на магистралях (принято):**
- Для `RoadKind::SixLane` (магистраль/хайвей) **тротуары не генерируем** и пешеходную связность **вдоль** неё не строим (пешеходы “не ходят вдоль хайвея”).
- Но **переходить магистраль на перекрёстках можно**: внутри `IntersectionCluster` формируем “угловые pedestrian nodes” (островки/углы), чтобы строить `Crosswalk` **через** SixLane-ногу перекрёстка.
- При этом **визуально оставляем reserve/отступ** под будущие тротуары/обочины (как часть “право‑проезда” дороги).
  Это нужно, чтобы потом включить тротуары на магистралях без полной переделки визуала.

### 5.6 Пешеходные переходы (crosswalks)

На каждом логическом перекрёстке генерируем переходы:
- для каждой “ноги” перекрёстка строим `Crosswalk`, **если** есть достижимые pedestrian nodes по обе стороны проезжей части (обычно это sidewalk nodes, а в случае магистрали — corner nodes внутри `IntersectionCluster`).
- это позволяет **запретить ходьбу вдоль SixLane**, но **разрешить переход** SixLane **в месте пересечения**.

```text
Crosswalk:
  - id
  - endpoints: два pedestrian nodes (обычно sidewalk nodes; для SixLane — corner nodes внутри `IntersectionCluster`)
  - geometry: polyline (обычно перпендикуляр к оси движения)
  - conflicts: зоны + коннекторы поворотов, пересекающие зебру
```

## 6) Микросим v2: автомобили (скорость, торможение, перестроения, обгоны)

### 6.1 Данные на машину

Предлагаем разнести данные на 3 уровня:

1) **Геометрия/тип** (почти не меняется):
- длина/ширина (для gap),
- max_speed_factor, max_accel, comfortable_decel.

2) **Профиль водителя** (поведение):
- aggression (как быстро хочет ехать и насколько охотно перестраивается),
- politeness (насколько учитывает ухудшение для других — параметр MOBIL),
- desired_headway_T, min_gap_s0,
- reaction_time (упрощённо — сглаживание).

3) **Текущее состояние движения**:
- `v` (скорость), `a` (ускорение),
- позиция на полосе: `(LaneId, s)` или “на маршруте”,
- цель/маршрут (destination),
- ближайший манёвр на перекрёстке (intention).

### 6.2 Продольная модель: IDM (Intelligent Driver Model)

IDM даёт реалистичное ускорение/торможение и волны пробок.

Обозначения:
- \(v\) — скорость,
- \(v_0\) — желаемая скорость,
- \(a\) — max accel,
- \(b\) — комфортное торможение,
- \(T\) — желаемый временной интервал (headway),
- \(s\) — текущий gap до лидера,
- \(\Delta v\) — относительная скорость \(v - v_{leader}\),
- \(s_0\) — минимальная дистанция.

Формулы:

\[
a_{idm} = a \left(1 - (v/v_0)^\delta - (s^\*/s)^2 \right)
\]

\[
s^\* = s_0 + vT + \frac{v\Delta v}{2\sqrt{ab}}
\]

Практика:
- clamp \(a_{idm}\) в диапазон \([-b_{max}, a_{max}]\),
- \(v_0 = \min(\text{speed_limit}, v_{driver})\),
- для стоп-линии/красного света можно моделировать **виртуального лидера** на расстоянии `d_stop`.

### 6.3 Поперечная модель: перестроения (MOBIL) + “держись правее”

**Цели перестроения:**
- “опережение” медленного лидера,
- подготовка к манёвру (налево/направо/прямо),
- уступить/влиться при сужении.

MOBIL (упрощённо) решает “стоит ли менять полосу”:
- **безопасность**: новый follower не должен получать торможение ниже порога;
- **выгода**: ожидаемое ускорение эго должно улучшиться;
- **вежливость**: учитываем потери ускорения у других.

Плюс “правило полосности”:
- при правостороннем движении: **держаться правее**, левую полосу использовать в основном для опережения/обгона и обязательных манёвров.

### 6.4 Опережение (в попутных полосах)

Поведение как в реальности:
1. Если впереди медленный лидер и есть безопасная левая полоса → перестроиться влево.
2. Ускориться до допустимой (обычно около лимита).
3. Обогнать.
4. Вернуться вправо при наличии безопасного окна и если больше нет причины быть слева.

Запреты (v2):
- не перестраиваться внутри перекрёстка;
- не “пилить” туда-сюда (вводим cooldown и пороги).

### 6.5 Обгон по встречке (двухполосные дороги 1+1)

Это самый рискованный манёвр и требует строгих условий, иначе нарушим требование “не нарушает”.

**Разрешаем только если:**
- дорога типа `TwoLane` (одна полоса в каждую сторону),
- впереди есть медленный лидер в своей полосе,
- до ближайшего перекрёстка/перехода/стоп-линии впереди **достаточно дистанции**,
- по встречной полосе в зоне видимости **нет** транспорта, либо time-to-collision больше времени обгона с запасом,
- манёвр можно завершить (вернуться) до появления конфликта.

**Оценка безопасности (минимальный расчёт):**

```text
пусть:
  v_ego = текущая скорость
  v_lead = скорость лидера
  v_on = скорость встречного (если есть)
  d_clear = расстояние до встречного по встречной полосе
  L_pass = дистанция, которую надо “набрать”, чтобы обогнать и вернуться:
           (gap_to_lead + lead_length + safety_margin)
  v_rel = max(v_ego_target - v_lead, eps)

t_pass ≈ L_pass / v_rel + t_lane_change_out + t_lane_change_in
t_collision ≈ d_clear / (v_on + v_ego_target)

условие: t_pass + margin < t_collision
```

**Состояния манёвра:**
- `OvertakeOncoming::PullOut`
- `OvertakeOncoming::Passing`
- `OvertakeOncoming::Return`
- `OvertakeOncoming::Abort` (если внезапно появилось препятствие — в v2 стараемся не допускать, стартуем только при строгом окне).

**Важно:** этот манёвр не должен попадать в pathfinding как “дешёвый путь”, иначе A* начнёт массово ездить по встречке.  
Обгон — **локальная тактика**, не часть стратегического маршрута.

### 6.6 Развороты (U-turn): где разрешены и как не “нарушать”

Требование: U-turn допустим, но должен оставаться **редким** и **строго безопасным**, чтобы не ломать ПДД и не превращаться в “чит”.

**Разрешаем U-turn в случаях:**

- **На перекрёстках**: если геометрия/коннекторы позволяют (манёвр `UTurn` как отдельный connector), и:
  - фаза светофора/право проезда разрешает,
  - нет конфликтов с пешеходными переходами,
  - выполнены резервации конфликтных зон (если включены).
- **В конце дороги (тупик)**: если впереди нет продолжения маршрута и нет ближайшего легального разворота.  
  В топологии это определяется как “нет выходящих рёбер вперёд по направлению движения” + есть физическое место.
- **Если машина застряла надолго**: как часть *формализованного* jam-recovery:
  - только после таймаута (**60 сек** сим-времени без прогресса),
  - только если вокруг есть безопасное окно и это не создаёт встречного конфликта,
  - не внутри перекрёстка.
- **Сервисные машины**: могут делать U-turn **в любом месте**, но всё равно с safety-check (без мгновенных телепортов).

**Важно:** U-turn не должен быть “оптимизацией маршрута”. Это *локальный* механизм выхода из тупика/ошибки/пробки.

### 6.7 Гарантия “не нарушает” и отсутствие коллизий

Чтобы действительно гарантировать отсутствие нарушений/столкновений:
- все решения принимаются “по правилам” + safety check,
- для перестроений используем двухфазное применение:
  1) собрать желания,
  2) разрешить только те, что не создают конфликтов (в том числе “двойное занятие”),
  3) применить.
- продольное движение считаем “front-to-back” на каждой полосе (сортировка по `s`).

## 7) Перекрёстки v2: приоритеты, светофор (1 на кластер), резервации

### 7.1 Без светофора: приоритеты и правило “помеха справа”

Текущие `IntersectionPriorityMarker` можно переиспользовать, но привязать к **IntersectionId**, а не к `TilePos`.

План:
- для каждого IntersectionCluster определить “главную дорогу” эвристикой:
  - выше `RoadKind.lanes()` → выше приоритет,
  - при равенстве — можно считать равноправным и применять “помеха справа”.
- назначить подходам приоритетные статусы:
  - `MainRoad` (едут первыми),
  - `Yield` (уступают),
  - `Stop` (обязательная остановка, затем уступают).

Реализм: “Stop” должен включать **полную остановку** хотя бы на минимальное время, даже если никого нет.

**Принято:** пока **без отдельных знаков** как инфраструктуры — приоритеты определяются автоматически “размером дороги”.  
**Будущая фича:** инструмент “дорожные знаки” (Stop/Yield/Main road) + сохранение/визуализация и влияние на симуляцию.

### 7.2 Светофор как контроллер IntersectionController (1 на IntersectionId)

**Критическое требование:** один светофор на один перекрёсток.

Значит, вместо `traffic_light_positions: HashSet<TilePos>` нужно:
- хранить `HashSet<IntersectionId>` (или map `IntersectionId -> TrafficLightControllerState`),
- иметь map `TilePos -> IntersectionId` (строится топологией).

UI команда `GameCommand::PlaceTrafficLight { pos: TilePos }` остаётся, но интерпретируется так:
1) найти `IntersectionId` по `pos`,
2) если у IntersectionId уже есть контроллер — удалить,
3) иначе — создать.

### 7.3 Как светофоры работают “в реальной жизни” (минимальная модель)

Минимальный реалистичный цикл:

1) **Green** для группы движений (например N-S straight+right)
2) **Yellow** для той же группы (предупреждение)
3) **All-Red clearance** (все стоят) 0.5–2.0 сек
4) Переключение на следующую группу (E-W straight+right)

Пешеходные сигналы:
- Walk (зелёный человечек) — разрешение перехода,
- Flashing Don’t Walk — “заканчивайте переход”,
- Don’t Walk — запрещено.

Упрощённая связка:
- Когда N-S зелёный, пешеходам разрешён переход **через E-W проезжую часть** (т.е. параллельно N-S потоку), потому что E-W транспорт стоит.
- Аналогично для E-W зелёного.

**Жёлтый и решение “тормозить или ехать”:**
- если при текущей скорости и комфортном торможении остановиться до стоп-линии нельзя → продолжаем движение (как в реальности),
- иначе останавливаемся.

**Поворот направо на красный (принято):**
- **Разрешён всегда** (в будущем — ограничения/уточнения через знаки/стрелки).
- Обязательное правило: **уступить пешеходам** на зебре (и не выезжать на переход, если он занят).
- Также это по сути “yield-манёвр”: на красный поворачиваем **только если безопасно** относительно конфликтующего транспорта (которому сейчас зелёный), желательно через admission/reservation.
- **Без обязательной полной остановки**: водитель снижает скорость до “скорости поворота” и при необходимости останавливается, если нет безопасного окна или есть пешеходы.
- **Если для пешеходов горит Walk**: поворот направо на красный всё равно формально разрешён, но на практике машина **ждёт**, пока пешеходы пройдут (yield).
- **Ограничение скорости поворота (принято):** при правом повороте на красный целевая скорость должна быть \(\le 15\) км/ч (≈ 4.2 м/с), пока манёвр не завершён.

### 7.4 Резервации конфликтных зон (опционально, но желательно)

Чтобы убрать deadlocks и сделать поведение строгим:
- Машина перед стоп-линией “запрашивает” коннектор + набор conflict zones на интервал времени.
- Контроллер перекрёстка выдаёт разрешение:
  - если фаза светофора разрешает манёвр,
  - если зоны свободны/не зарезервированы,
  - и если выходная полоса имеет место (don’t block the box).

Если разрешение не выдано — машина ждёт.

Плюсы:
- гарантируем отсутствие столкновений в перекрёстке,
- резко уменьшаем необходимость читерных unstuck-операций.

## 8) Пешеходы v2: тротуары, маршруты, переходы, конфликты

### 8.1 Пешеходная топология

- Sidewalk graph: узлы вдоль дорог (world coords), рёбра — сегменты тротуара.
- Crosswalk edges: рёбра, пересекающие проезжую часть на перекрёстках.

Пешеходы не ходят по lane tiles.

### 8.1.1 Скорость пешехода (принято)

- Базовая скорость пешехода: **1.4 м/с** (≈ 5 км/ч).
- Эта скорость используется для:
  - оценки времени перехода (нужно для “окна безопасности” на нерегулируемых зебрах),
  - расчёта длины/времени пешеходных маршрутов для `WalkTour` и порога **800 м**.

### 8.2 Поведение пешехода на переходе

Если перекрёсток со светофором:
- **строго ждать зелёного** сигнала (Walk) для нужного перехода;
- **начинать переход только на Walk** (на “Flashing” не стартуем; flashing, если появится в симуляции, трактуем как “разрешено закончить, но не начинать”).

Если перекрёсток без светофора:
- ждать безопасного окна по конфликтующим коннекторам (или по ближайшим автомобилям на подходах),
- после начала перехода — машины должны уступать (в т.ч. при повороте).

**Принято (нерегулируемые переходы):** на переходах без светофора пешеходы **не идут “внаглую”**, а ждут окно безопасности; машины, приближаясь к зебре, должны уступать пешеходам, уже начавшим переход.
**Уточнение (принято):** на нерегулируемых зебрах машины обязаны уступать **пешеходам, которые уже находятся на переходе**; пешеходы, которые ещё не вышли на переход, продолжают ждать безопасного окна.

**Переход магистрали без светофора (принято):**
- Даже если пересекаемая “нога” перекрёстка — `RoadKind::SixLane`, переход **разрешён** без светофора.
- Алгоритм окна безопасности должен быть более консервативным на многополосных переходах:
  - пешеход должен иметь окно, достаточное чтобы **завершить переход всей ширины** (время = длина перехода / 1.4 м/с + safety margin),
  - окно должно быть безопасным относительно конфликтующих транспортных потоков (в т.ч. поворотов).

**Политика “долго ждёт окно” (принято: reroute):**
- Если пешеход ожидает на нерегулируемом переходе слишком долго, он **перестраивает маршрут** (вариант B).
- Рекомендуемый параметр: `PED_WAIT_REROUTE_SECS = 60` сек (сделать конфигом).
- Рерутинг должен:
  - предпочитать переходы/перекрёстки со светофором;
  - предпочитать переходы через дороги меньшего класса (TwoLane/FourLane) перед SixLane;
  - ограничивать число попыток (принято: `PED_WAIT_REROUTE_MAX_ATTEMPTS = 3`) и радиус поиска альтернативы, чтобы не было бесконечных циклов.

### 8.3 Взаимодействие “поворот + зебра”

Реалистичное правило:
- при повороте направо/налево водитель **уступает** пешеходу на зебре, если пешеход пересекает траекторию.

Технически:
- crosswalk конфликтует с turn-коннекторами,
- активный/зарезервированный turn-коннектор блокируется, если на crosswalk есть пешеходы, и наоборот.

## 9) Интеграция с trips/citizens

Сейчас `Citizen` генерирует `TripRequested(from, to, purpose)` и трафик спавнит машину (машина “появляется” на точке старта поездки).

**Принято:** в v2 вводим **полноценных пешеходов** (визуально — маленький квадратик/точка) и выбор режима поездки:
- **либо пешком, либо на машине**;
- **без “машины из кармана”**: если гражданин уехал на машине, он возвращается на этой же машине; если ушёл пешком — возвращается пешком.

### 9.0 Автовладение (принято сейчас, будущая экономика позже)

- **Сейчас (v2 MVP)**: считаем, что **у каждого горожанина есть машина** (100% автодоступность).
- **Будущая фича** (когда расширим зонирование/экономику): горожане **покупают машины** в ретейле/торговле, автопарк становится ограниченным ресурсом (car ownership rate становится следствием экономики).

### 9.1 Mode choice как “тур” (туда-обратно)

Чтобы соблюсти запрет “достать машину из кармана”, вводим понятие **тура**:
- тур начинается в `AtHome` и заканчивается, когда гражданин снова в `AtHome`;
- **режим тура фиксируется** при старте: `WalkTour` или `CarTour`;
- все ноги внутри тура используют один режим.

Это хорошо ложится на текущие состояния (`AtHome → ToWork/ToShop → ... → ToHome → AtHome`).

**Правило выбора режима (принято):**
- если существует пешеходная связность (маршрут по `Sidewalk/Crosswalk` графу существует) и длина пешеходного пути \(\le 800\) м → `WalkTour`;
- иначе → `CarTour`.

**Уточнение (принято):** метрика 800 м считается как **длина маршрута по пешеходному графу** (sidewalk/crosswalk edges), а не “по воздуху”.

При масштабе \(T=10\) м/тайл это соответствует порогу примерно **80 тайлов** пешеходного пути (если считать по длине графа в метрах).

### 9.2 Пешком (WalkTour)

- При старте тура создаём `Pedestrian` entity и строим маршрут по `Sidewalk/Crosswalk` графу.
- На прибытии в цель пешеход либо стоит “точкой” у здания, либо может быть скрыт/деспавнен (оптимизация), но **следующий leg тура** всё равно считается пешим.

### 9.3 На машине (CarTour) и “не из кармана”

Ключевое: машина должна быть **связана с гражданином** и **не исчезать** на месте назначения.

Минимальная модель (без полноценной парковочной системы; парковка абстрактно “внутри здания”):
- на старте тура спавним (или “активируем”) `Vehicle` **у дома**;
- по прибытии к месту назначения **не оставляем машину стоять на дороге**:
  - машина “заезжает” в здание/на участок и становится **неактивной** (не блокирует поток),
  - технически это может быть “despawn entity + сохранить CarAsset в данных гражданина”, либо “invisible/inactive entity” — важно, что это *не новая машина из воздуха*;
- при следующем leg тура “активируем” машину снова от здания (как из гаража/парковки) и строим новый маршрут.

**Аналогично для сервисных машин (принято):**
- по завершении задачи сервисная машина “возвращается” и хранится абстрактно в здании службы, **не занимая lane tiles**.
  Это исправляет текущую ситуацию, где сервисные машины могут “стоять на дороге”.

Это гарантирует: нельзя поехать домой на машине, если ты пришёл пешком, и нельзя создать новую машину “из воздуха” на работе/в магазине.

### 9.4 Привязка к зданиям (без изменения футпринтов)

Пока футпринты зданий не меняем: `Building.pos` — якорная клетка.
- Для пешеходов: “дверь” здания проецируем на ближайший sidewalk node.
- Для машин: точку старта/финиша маршрута ищем как ближайший доступный lane tile (как сейчас `adjacent_road_towards`), после чего машина “въезжает” в здание и становится неактивной (абстрактная парковка).

Это позволит реально использовать пешеходов, а не только как декоративных агентов.

## 11) Тестирование и отладка (что нужно заложить в дизайн)

### 11.1 Юнит-тесты (логика)

- кластеризация IntersectionCluster (простые и многополосные случаи),
- расчёт подходов/стоп-линий,
- state machine светофора (green/yellow/all-red),
- IDM: остановка до стоп-линии, устойчивость к лидеру,
- MOBIL: безопасность перестроения,
- обгон по встречке: проверка безопасного окна.

### 11.2 Сценарии (интеграционные)

- 2×2 перекрёсток (TwoLane×TwoLane) со светофором: очередь, смена фаз, “не блокировать перекрёсток”.
- 4×4 перекрёсток (FourLane×FourLane): повороты, перестроения под манёвр.
- Пешеходы на зебре + поворотный поток: поворачивающие уступают.
- Правый поворот на красный: поворачивающий уступает пешеходам и конфликтующему потоку.
- Пересечение с SixLane: пешеходы **не ходят вдоль** хайвея, но могут **перейти** его на перекрёстке.
- Пешеход на нерегулируемой зебре “ждёт слишком долго” → срабатывает reroute к альтернативному переходу.
- Mode choice (800 м): цель на ~700 м по пешеходному графу → `WalkTour`; цель на ~900 м → `CarTour`; режим сохраняется “туда-обратно”.
- Двухполосная дорога 1+1: медленный лидер + встречный → запрет обгона; без встречного → разрешён обгон.

### 11.3 Debug overlays (для разработки)

- отрисовка IntersectionCluster (AABB, id),
- отображение активной фазы светофора и разрешённых коннекторов,
- heatmap занятости полос (как сейчас) + доп. слой “скорости/задержки”,
- визуализация траекторий коннекторов и crosswalks,
- подписи над машинами: v, a, state, target lane.

   **Принято:** \(T = 10\) м (участок 2×3 тайла = 20×30 м).
2. **Turn lanes (`lane_type`)**:  
   - **Сейчас (v2 MVP)**: автогенерация системой (эвристики по типу дороги/подходу/нагрузке).  
   - **Позже (отдельная фича)**: *инструмент для игрока* для ручной разметки turn lanes и стрелок — требует отдельного дизайна UX/баланса/сохранений.
3. **UTurn**: **принято** — разрешаем на перекрёстках, в тупиках, при длительном застревании; сервисным — в любом месте (с safety-check).
4. **Тротуары на магистралях (`RoadKind::SixLane`)**: **принято** — пока отключены, но визуальный reserve под них оставляем.
5. **Экстремальный джем/тупики**: какой policy после таймаута “застряла” (принято: 60 сек)?  
   Предложение: сначала safety U-turn → затем “эвакуатор/деспаун” редких несервисных машин, но без нарушения правил движения.
6. **Пешеход “долго ждёт окно”**:  
   - **Принято:** `PED_WAIT_REROUTE_SECS = 60`, `PED_WAIT_REROUTE_MAX_ATTEMPTS = 3`.  
   - Остаётся решить: радиус/стратегия поиска альтернативного перехода, чтобы reroute был быстрым и не создавал циклы.

## 13) Заключение

Этот документ описывает полную переработку трафика “вглубь” (правила + динамика + перекрёстки + пешеходы) и одновременно опирается на текущую сильную сторону проекта — lane-тайлы и A*/графовую инфраструктуру.  
Ключевой сдвиг v2: **логический перекрёсток** и **контролируемые манёвры** (IDM/MOBIL + admission), что позволяет реально обеспечить требование: “трафик слушается правил и не нарушает”.
